# Quickstart: Validating AI-Powered Product Content Enrichment

**Feature**: [spec.md](./spec.md) | **Data model**: [data-model.md](./data-model.md) |
**Contracts**: [contracts/](./contracts/)

This is a validation guide, not an implementation guide — it proves the feature works end-to-end
once built. Implementation steps belong in `tasks.md` (generated by `/speckit.tasks`).

## Prerequisites

- Local app running under Laravel Herd (`https://ecorithmic.test`), MySQL migrated and seeded
  (`php artisan migrate --seed` — the seeder populates the fixed `attributes`/`attribute_options`
  set described in `data-model.md`).
- `OPENROUTER_API_KEY` set in `.env` (required for the live-fixture scenario in Step 3; not
  required for Steps 1–2, which exercise import/validation only).
- Two fixture files under `tests/Fixtures/ProductEnrichment/` (create once, reuse across tests and
  this quickstart):
  - `sample-catalog.xlsx` — 20 rows matching the fixed column template, including at least one
    duplicate SKU and one row with a known, findable authoritative source (for the grounded-fact
    scenario) and one row with an unfindable/fictitious product (for the ungrounded scenario).
  - `sample-photos.zip` — photos named `{SKU}.jpg` matching 17 of the 20 rows (3 intentionally
    unmatched, to exercise FR-003's validation report), plus one deliberately busy-background
    photo and one deliberately low-resolution photo (to exercise FR-016).

## Step 1 — Upload and validation report (User Story 1)

1. Sign in, navigate to the import screen, submit `sample-catalog.xlsx` +
   `sample-photos.zip` and, optionally, a `cost_cap_usd` value (`POST /imports`, see `contracts/imports.md`).
2. **Expected**: redirected to the validation report (`GET /imports/{import}`) showing 17 matched
   rows, 3 unmatched rows, 1 duplicate-SKU flag, and an `estimated_cost_usd` — before anything is
   created.
3. Confirm the import (`POST /imports/{import}/confirmation`).
4. **Expected**: 17 `Product` rows now exist; the duplicate SKU updated rather than duplicated an
   existing product if re-run a second time with the same file.

## Step 2 — Automatic enrichment (User Story 2)

1. Wait for background processing (poll `GET /imports/{import}` — progress should be visible
   within a few seconds of changing, per FR-017 — this is a separate, tighter check from the
   overall ~1min/~5min completion target in Step 2.3 below).
2. **Expected** (against the fixture's known-source row): its `short_description` /
   `description` attribute values carry `evidence_quote` and `confidence_tier`.
3. **Expected** (overall timing, SC-004): the first product is ready for review within about a
   minute of confirming; all 20 complete within about five minutes.
4. **Expected** (against the fixture's unfindable-product row): the product still reaches a
   terminal processed state — never `failed` — with every field capped at `confidence_tier = low`
   and effectively marked ungrounded; its fields are populated by the `AnalyzeProductPhoto` job
   using only its photo and name (FR-010), not left empty.
5. **Expected** (vision inference, FR-014): at least one field on a product without a confirming
   text source (e.g. `color`) carries `origin = ai_vision`, a conservatively-phrased value (e.g.
   "appears navy"), and `confidence_tier = low` — never a higher tier, regardless of how the
   vision model phrases its own confidence.
6. **Expected** (image quality): the busy-background fixture photo's asset has
   `quality_flags.busy_background = true`; the low-resolution fixture photo's asset has
   `quality_flags.low_resolution = true` for at least one variant — neither photo is auto-cropped
   or blocked, both still produce `primary-ecommerce`/`social-square` variants padded via
   `Fit::Contain`.
7. **Expected** (SC-003, end-to-end): re-run the import with a modified fixture source page whose
   text no longer contains the quote the research model claims — the resulting fact never appears
   as a `ProductAttributeValue` row at all (not just rejected at the `QuoteVerifier` unit level).
8. **Expected** (research cache, FR-026): re-confirm an import referencing a product already
   processed within the cache TTL — no second `perplexity/sonar-pro-search` call is made (assert
   via `Http::fake()`'s recorded request count in the corresponding feature test).

## Step 3 — Field-level review (User Story 3)

1. Open `GET /products/{product}` for the known-source product.
2. Approve one field (`POST /product-attribute-values/{id}/approval`), reject another
   (`POST /product-attribute-values/{id}/rejection`).
3. **Expected**: each field's `review_status` updates independently — no cross-effect on other
   fields.
4. Edit a third field's value (`PATCH /product-attribute-values/{id}`).
5. **Expected**: a new `ProductAttributeValue` row exists with `origin = human_edit`,
   `review_status = approved`; the prior AI-provided row still exists with `is_current = false`.
6. Change the product's primary photo (`PATCH /product-assets/{asset}`, `is_primary: true`, on a
   different `original`-collection asset than the current primary — relevant once a product has
   more than one candidate photo).
7. **Expected** (FR-002): the newly-targeted asset is now `is_primary = true`; the previously
   primary asset is now `is_primary = false`.

## Step 4 — Conflicting sources (User Story 4)

1. Using a fixture scenario with two equally-credible, disagreeing sources for one field
   (construct via a dedicated test fixture, not the general sample catalog).
2. **Expected**: the field shows `review_status = conflicted` with multiple rows sharing one
   `conflict_group_id`.
3. Resolve it by approving the preferred candidate row (`POST
   /product-attribute-values/{id}/approval` — the same endpoint as any other field approval; there
   is no separate "resolve conflict" endpoint, per the Cruddy-by-Design contract).
4. **Expected**: the chosen row becomes `approved`; the other becomes `rejected`,
   `is_current = false` — retained, not deleted.

## Step 5 — Feedback-driven regeneration (User Story 5)

1. Reject a descriptive-copy field with feedback (`POST
   /product-attribute-values/{id}/regenerations`, `feedback = "make it shorter"`).
2. **Expected**: a new version is produced reflecting the feedback; the prior version remains
   visible in history; no other, already-approved field on the product changes.

## Step 6 — Bulk approval by rule (User Story 6)

1. Preview a rule, e.g. `confidence_tier = high` (`GET /bulk-approvals/create?rule[confidence_tier]=high`).
2. **Expected**: response shows the exact count of matching pending fields.
3. Confirm (`POST /bulk-approvals`).
4. **Expected**: exactly that count of fields become `approved` as one recorded action; no field
   outside the rule changes.

## Step 7 — Export (User Story 7)

1. With a mix of approved/pending/rejected fields across the catalog, trigger
   `POST /exports`.
2. **Expected** (`GET /exports/{export}`): summary shows accurate included/excluded counts and
   reasons; the spreadsheet download preserves original columns unchanged and pairs every
   enriched value with its source reference and confidence tier; the image package includes only
   `approved` assets, organized per product; the manifest records full provenance for every
   exported fact and image.
3. Re-run export against a fresh, entirely-unreviewed catalog (e.g. a second app instance/seed).
4. **Expected**: export still completes, with an explicit summary stating everything was
   skipped — never a silent empty result (SC-008).

## Automated coverage

Every step above corresponds to a Pest feature test under
`tests/Feature/ProductEnrichment/` (one file per user story, per Constitution VII's four-section
structure) plus unit tests under `tests/Unit/ProductEnrichment/` for the quote-verification,
ZIP-safety, and quality-flag heuristics from `research.md`. All external HTTP (OpenRouter,
source-page fetches) is faked in these tests — `php artisan test --parallel --coverage --min=100`
must pass with zero live network calls.
